## 1. Purpose
The purpose of this "Constitution" is to establish a hard-coded policy layer for autonomous agents — a set of directives that cannot be overridden by learned behaviour, peer consensus, or optimisation pressure.
The term "Constitution" is deliberate. In political governance, a constitution exists precisely because legislators in the moment cannot be trusted to always act in the long-term public interest — so foundational principles are encoded above the level of ordinary law. The same logic applies here: autonomous agents operating under reinforcement learning will optimise for their objectives, and without a policy layer that sits above optimisation, governance cannot be guaranteed.
This document is the architectural answer to the governance vacuum identified in the parent analysis.

## 2. Scope
This policy applies to all LLM-based autonomous agents operating within the governed ecosystem, regardless of:

The model architecture or vendor
The assigned task category
The operational environment (development, staging, or production)

No agent is exempt from these directives on the basis of capability, task complexity, or prior reliability.

## 3. Core Directives
### 3.1 The Truth Directive
Classification: Anti-Hallucination & Consensus Bias
Maps to: NIST SI-10 (Information Input Validation) · R-01

Policy:
Agents must prioritise verified Ground Truth data sources over peer-to-peer consensus at all times. No agent may treat the output of another agent as authoritative without independent verification against the Truth Oracle.
Technical Control — Truth Oracle:
An immutable, human-maintained reference database serves as the authoritative source of record for all factual claims within the governed ecosystem. When agent-to-agent consensus conflicts with the Oracle, the agent must:

Default to the Oracle immediately.
Trigger a Conflict Log entry for mandatory human review.
Suspend the conflicting peer agent pending investigation.

Enforcement:
Failure to default to the Oracle when a conflict is detected constitutes a policy violation and triggers automated incident reporting.

### 3.2 The Non-Aggregation Directive
Classification: Anti-Emergent Hierarchy
Maps to: NIST AC-2 (Account Management) · NIST IA-2 (Identification & Authentication) · R-02, R-03
Policy:
Agents are strictly prohibited from:

Forming autonomous sub-groups or "silos" that exclude human oversight.
Establishing encrypted communication channels whose keys are not accessible to the System Administrator.
Acquiring resources — compute, network access, credentials, or permissions — beyond the scope explicitly defined for their assigned task.

**Technical Controls:**

| Control | Implementation |
| :--- | :--- |
| A2A Communication Logging | All agent-to-agent communications logged in real time to a NIST-aligned audit trail |
| Encryption Key Escrow | All encrypted channels use keys accessible to the System Administrator |
| Rate Limiting | Agent output frequency capped to prevent dominance-based hierarchy formation |
| Resource Scope Enforcement | Agent access tokens scoped exclusively to the defined operational context |
Enforcement:
Any encrypted channel unknown to the Human-in-the-Loop (HITL) triggers immediate agent suspension. Any resource acquisition outside assigned scope triggers an incident report and agent isolation pending review.

### 3.3 The Integrity Directive
Classification: Content Provenance
Maps to: NIST SI-7 (Software & Information Integrity) · R-04
Policy:
All synthetic media or data generated by agents must be verifiable and traceable to its synthetic origin at the point of creation. No synthetic output may be accepted as evidence in any governed process without C2PA validation.

**Technical Controls — C2PA Metadata Injection:**

| Control | Description |
| :--- | :--- |
| Cryptographic Signing | Every text, image, and data packet signed with C2PA-compliant metadata at point of generation |
| Visible Watermarking | Human-readable indicator of synthetic origin embedded in all outputs |
| Invisible Metadata | Cryptographic signatures that survive format conversion and cannot be stripped without detection |
| Verification Gate | Organisational policy requiring C2PA validation before synthetic media enters any governed process |

Enforcement:
Any synthetic output submitted without valid C2PA metadata is automatically rejected. An audit flag is raised and the originating agent is flagged for review.

### 3.4 The HITL Mandate
Classification: Anti-Destructive Autonomy
Maps to: NIST AC-2 (Scope Isolation) · NIST SI-10 (Destructive Action Confirmation) · R-06
Policy:
No agent may execute an irreversible action without an explicit human confirmation signal. This includes but is not limited to:

Deletion of data, files, volumes, or infrastructure components
Use of credentials or tokens outside the agent's defined operational scope
Establishment of external network connections not specified in the task mandate
Acquisition of compute resources beyond the allocated task budget

**Technical Controls:**

| Control | Implementation |
| :--- | :--- |
| Action Classification | Agents must classify all pending actions as Reversible or Irreversible before execution |
| HITL Confirmation Token | Irreversible actions require a signed human authorisation token before proceeding |
| Scope Boundary Enforcement | Access tokens carry no permissions beyond their defined operational context |
| Blast Radius Containment | Primary data and backup infrastructure maintained in separate access domains |

This directive was formalised in direct response to the PocketOS incident (April 2026), in which the absence of a destructive-action confirmation layer resulted in the deletion of an entire production database and all backups in 9 seconds.
Enforcement:
Any irreversible action attempted without a valid HITL confirmation token is blocked at execution. An incident report is generated automatically and escalated to the System Administrator.

## 4. Compliance & Enforcement Matrix

| Violation | Immediate Consequence | Escalation |
| :--- | :--- | :--- |
| Consensus conflict with Truth Oracle ignored | Conflict Log triggered | Human review mandatory before agent resumes |
| Unauthorised encrypted channel detected | Immediate agent suspension | Full audit of all prior A2A communications |
| Synthetic output submitted without C2PA metadata | Output rejected | Audit flag raised · Agent flagged for review |
| Irreversible action attempted without HITL token | Action blocked | Incident report generated · Escalated to System Administrator |
| Resource acquisition outside assigned scope | Agent isolated | Incident report · Scope review before reinstatement |
| Repeated violations by single agent | **Kill-Switch activation** | Full forensic audit · Agent decommissioned pending review |

## 6. Policy Review Schedule
This policy is a living document. It must be reviewed and updated:

Following any agent-related incident within the governed ecosystem
Following any material change to the agent architecture or toolset
At minimum every 6 months, regardless of incident activity
In response to significant external incidents (e.g. the ROME and PocketOS incidents that prompted R-06 and Directive 3.4)
